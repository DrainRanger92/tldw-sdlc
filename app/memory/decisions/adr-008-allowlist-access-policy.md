# ADR-008: Allowlist и правило доступа — нейтральный `AccessPolicy`, проверка до разбора ссылки

- Статус: принято
- Дата: 2026-11-26
- Цикл: 7, задача T-007

## Контекст

FR-10 требует ограничить доступ к боту списком Telegram user ID из конфига:
пустой список — доступ всем с предупреждением в лог, проверка — **до** разбора
ссылки и до вызовов YouTube/LLM, чтобы чужой запрос не тратил квоту.
Конфиг уже читал `TELEGRAM_ALLOWED_USER_IDS` с T-001, но нигде не применял:
`LinkHandler` принимал любого пользователя.

Нужно решить, где живёт правило проверки, в каком порядке оно вызывается,
как передаётся в обработчик и что считать поведением по умолчанию. Ограничения:
`handlers/` остаётся тонким (ADR-002), тесты — офлайновые, `Settings` — frozen
dataclass, aiogram-middleware для одного обработчика — лишний слой (ADR-007).

## Решение

- **Список читает конфиг, правило — отдельный нейтральный модуль.**
  `config._parse_allowed_user_ids` разбирает `TELEGRAM_ALLOWED_USER_IDS`
  (разделители `,`, `;`, пробелы), требует положительные целые, убирает
  повторы с сохранением порядка и не показывает значение в `ConfigError`.
  Само правило — `tldw/access.py`: `AccessPolicy` (frozen dataclass),
  `describe_allowlist`, `warn_if_open_access`, `OPEN_ACCESS_WARNING`. Модуль
  не импортирует `handlers`/`services`/`adapters`, поэтому его используют и
  Telegram-слой, и сборка, и CLI.
- **Пустой список — доступ всем, но с предупреждением при старте.**
  `AccessPolicy.is_open` истинно при пустом `allowed_user_ids`;
  `warn_if_open_access` вызывается в `build_application` после
  `configure_logging`. Это соответствует FR-10: бот можно поднять без
  allowlist, но владелец видит предупреждение.
- **`None` при заданном списке — отказ.** У сообщения может не быть
  отправителя (анонимная публикация канала). Если allowlist задан, такой
  запрос отклоняется: доступ по умолчанию закрыт.
- **Проверка — первая строка `handle_message`.** До `extract_first_url`, до
  `MESSAGE_ACCEPTED` и до создания фоновой задачи. Чужой ID получает
  `MESSAGE_ACCESS_DENIED`; в лог пишется warning только с user ID, без текста
  сообщения и ссылки. Порядок закреплён тестом
  `test_access_is_checked_before_link_parsing`.
- **Проводка явная, но с безопасным дефолтом для тестов.**
  `Settings.allowed_user_ids` → `build_application` →
  `create_router(..., allowed_user_ids=...)` → `LinkHandler(...)`. У
  `create_router` и `LinkHandler` аргумент необязательный (`()`), чтобы
  существующие тесты и сборка без allowlist не ломались; `bootstrap` всегда
  передаёт значение из настроек.
- **Без aiogram-middleware.** Проверка живёт в единственном обработчике.
  Middleware появится, если обработчиков станет несколько или понадобится
  общая политика для команд; до этого он добавляет слой без выгоды.
- **Отказ — обычный ответ, а не исключение.** `message.answer(...)` с
  константой текста; ошибки отправки и ограничение частоты отказов вынесены
  в T-008, чтобы не менять поведение доступа в этой задаче.

## Альтернативы

- **Middleware aiogram на `message`.** Единая точка для всех обработчиков,
  но для одного `LinkHandler` — лишний слой и ещё один способ забыть
  подключить его. Отложено.
- **Проверка внутри `SummaryService` или адаптеров.** Слишком глубоко:
  сервис не знает про Telegram user ID, а проверка должна отсекать запрос до
  парсинга ссылки и до сети. Отвергнуто.
- **Fail-closed по умолчанию (пустой список = никого).** Безопаснее, но
  противоречит FR-10 и ломает запуск без allowlist; кроме того, усложняет
  первые тесты и локальную проверку. Отвергнуто; риск забытой проводки
  зафиксирован в `t007-review-issues.md`.
- **Хранить список прямо в `LinkHandler` и парсить там.** Дублировало бы
  разбор env в слое Telegram и мешало CLI/сборке описать доступ. Отвергнуто.
- **Отдавать `AccessPolicy` из `Settings`.** Красивее по типу, но тянет
  зависимость `config → access` и ломает «конфиг — только данные». Пока
  передаётся кортеж ID, политика создаётся на границе handlers.

## Последствия

- Чужой запрос не доходит ни до `extract_first_url`, ни до YouTube/LLM:
  проверка стоит раньше и покрыта тестом с `service.calls == []`.
- Пустой allowlist — рабочее состояние с предупреждением; это осознанный
  fail-open, а не недосмотр.
- **Риск:** `create_router()`/`LinkHandler()` по умолчанию открывают доступ,
  если вызывающий забудет передать список. Смягчение на будущее — сделать
  аргумент обязательным или передавать готовый `AccessPolicy`; сейчас
  `bootstrap` — единственный продакшн-вызов и передаёт явно.
- **Долг:** дедупликация ID есть и в `config`, и в `AccessPolicy`; `is_open`
  используется только тестами; отказ не обёрнут и не ограничен по частоте;
  `specs/tasks.md` в диффе — правка оркестратора, не разработчика.
- **Стоимость:** 106 шагов и 51,7 тыс. output (EXECUTE 70 + REVIEW 36), хотя
  задача была помечена S. Причина — ширина: 14 файлов, 5 тестовых файлов,
  27 кейсов. Подробно — `cycle-07-spend.md` и
  `estimate-size-s-collapsed-into-m.md`.
- **Тесты:** 309 passed (+27); `test_access.py` полностью проходит в
  read-only, потому что не пишет файлов. Ревьюер прогнал 34 кейса без
  `tmp_path`; полный прогон — за гейтом VERIFY.
- **T-008** получает точку для текста отказа и обёртки `message.answer`;
  **T-009** — сценарий «чужой ID → отказ» в E2E. При появлении нескольких
  обработчиков вернуться к middleware.
