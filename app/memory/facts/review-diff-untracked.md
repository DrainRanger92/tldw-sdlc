# Ревью и untracked-файлы: `git diff` не показывает новый код

Дата: 2026-11-26. Наблюдение по циклу 1 (T-001).

## Что произошло

Ревьюеру передали «`git diff` против `8c9c46e`» и статистику диффа.
В статистике был только `specs/001-mvp/tasks.md` (2 строки: статус T-001
и перенос секции), потому что весь новый код — `app/main.py`,
`app/pyproject.toml`, `app/tldw/`, `app/tests/`, `app/.env.example` —
на момент ревью был **untracked**. `git diff` по определению не показывает
неотслеживаемые файлы.

Ревьюер сделал 23 шага, потратил 29,5 тыс. нового input, читал файлы
напрямую и сам отметил в отчёте: «diff stat misleading; real work is
21 untracked files under app/». Цикл получил APPROVE. Но формальное
доказательство в промпте было неполным: по диффу нельзя было убедиться,
что новый код вообще существует и покрыт критериями.

## Риск

Менее внимательный ревьюер может одобрить изменение, не увидев основной
код. Для цикла, который создаёт файлы с нуля, это систематическая слепая
зона, а не разовая случайность.

## Что делать в следующих циклах

- Перед ревью делать `git add -N app/` (intent-to-add), чтобы новые файлы
  попали в `git diff`, либо передавать ревьюеру `git status --porcelain -uall`
  и явный список untracked-файлов.
- В промпт ревью добавлять требование: «проверь, что каждый новый файл
  из `git status` попал в анализ; если дифф пуст, а файлы новые — читай
  их напрямую».
- Не считать `git diff --stat` полным описанием изменения, пока в рабочей
  копии есть untracked-файлы.

## Повторение в цикле 2 (T-002)

Паттерн повторился: в промпте ревью был `git diff --stat` из пяти файлов,
а `app/tldw/services/note.py` и `app/tests/test_note.py` были untracked и в
статистику не попали. Ревьюер сам заметил это и прочитал оба файла, но
отметил: «ревьюер, доверяющий diffstat, одобрил бы пустое изменение».
Коммит оркестратора использует `git add -A`, поэтому код не потерялся;
неполным было именно доказательство на ревью.

Итого 2 из 2 циклов: перед ревью новые файлы не попадали в дифф. Паттерн
вынесен в скил `app/skills/review-handoff/SKILL.md` (подготовка рабочей копии
и сверка `git status -uall` с diffstat).

Это наблюдение про гейт оркестратора; в LEARN код и `orchestrator/`
не меняются, поэтому зафиксировано в памяти и скиле `review-handoff`.

## Цикл 3 (T-003): паттерн закрыт процессом

Разработчик выполнил `git add -N` для `app/tldw/adapters/youtube.py` и
`app/tests/test_youtube_adapter.py` до подготовки диффа. Ревьюер получил
`git status -uall` ровно из 6 путей, совпавших с diffstat, и явно отметил,
что посторонних untracked-файлов нет. Слепая зона исчезла: 2 из 2 циклов до
введения `git add -N` и 1 из 1 после. Требование остаётся в чек-листе
`review-handoff`: если после `add -N` появился ещё один новый файл, процедуру
нужно повторить.

## Цикл 4 (T-004): процесс подтверждён

Разработчик снова выполнил `git add -N app/` перед подготовкой диффа.
`git status --porcelain -uall` показал 9 файлов в `app/` плюс правку
`specs/001-mvp/tasks.md`; все 9 файлов (`llm.py`, три ресурса, тесты,
`__init__.py`, `pyproject.toml`, `CHANGELOG.md`) попали в
`git diff --stat 210d83b -- app`; ревьюер прочитал новый код и ресурсы, а не
только diffstat. Итог после исправления — **2 из 2 циклов**: процедура
работает, если её не забыть. Ревьюер по-прежнему видит изменённый
`specs/001-mvp/tasks.md`; это правка оркестратора, а не разработчика (см.
`t004-review-issues.md`).
