# Ревью и untracked-файлы: `git diff` не показывает новый код

Дата: 2026-11-26. Наблюдение по циклу 1 (T-001).

## Что произошло

Ревьюеру передали «`git diff` против `8c9c46e`» и статистику диффа.
В статистике был только `specs/001-mvp/tasks.md` (2 строки: статус T-001
и перенос секции), потому что весь новый код — `app/main.py`,
`app/pyproject.toml`, `app/tldw/`, `app/tests/`, `app/.env.example` —
на момент ревью был **untracked**. `git diff` по определению не показывает
неотслеживаемые файлы.

Ревьюер сделал 23 шага, потратил 29,5 тыс. нового input, читал файлы
напрямую и сам отметил в отчёте: «diff stat misleading; real work is
21 untracked files under app/». Цикл получил APPROVE. Но формальное
доказательство в промпте было неполным: по диффу нельзя было убедиться,
что новый код вообще существует и покрыт критериями.

## Риск

Менее внимательный ревьюер может одобрить изменение, не увидев основной
код. Для цикла, который создаёт файлы с нуля, это систематическая слепая
зона, а не разовая случайность.

## Что делать в следующих циклах

- Перед ревью делать `git add -N app/` (intent-to-add), чтобы новые файлы
  попали в `git diff`, либо передавать ревьюеру `git status --porcelain -uall`
  и явный список untracked-файлов.
- В промпт ревью добавлять требование: «проверь, что каждый новый файл
  из `git status` попал в анализ; если дифф пуст, а файлы новые — читай
  их напрямую».
- Не считать `git diff --stat` полным описанием изменения, пока в рабочей
  копии есть untracked-файлы.

Это наблюдение про гейт оркестратора; в LEARN код и `orchestrator/`
не меняются, поэтому зафиксировано только в памяти.
