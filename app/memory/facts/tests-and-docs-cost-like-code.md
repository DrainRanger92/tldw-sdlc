# Задача без продакшн-кода стоит как M: T-009 дала 178 шагов и 154,7 тыс. output

Дата: 2026-11-26. T-009 формулировалась как «добавить сквозной тест и README»
и была помечена **S**. В диффе цикла — **одна строка продакшн-кода**
(версия в `tldw/__init__.py`), а расход — 178 шагов, 154,7 тыс. output и
11,82 млн токенов: больше, чем любая кодовая задача проекта. Причина не в
объёме, а в **ширине поверхности проверки** и в двух раундах ревью.

## Что именно стоило шагов

| Работа | Объём | Чем стоила |
|---|---|---|
| `tests/support.py` | 272 строки, новый | общий каркас: `Harness`, `make_harness`, `run_message`, фейковые источник/суммаризатор, константы видео |
| `tests/test_e2e.py` | 224 строки, 5 кейсов | настоящий `Dispatcher` → `LinkHandler` → `SummaryService` → `storage`; подменены только Telegram/YouTube/LLM |
| `tests/test_readme.py` | 118 строк, 23 проверки | README как исполняемый контракт: команды, все env-переменные, ручной сценарий, сканер секретов по `app/**/*.py` |
| `app/README.md` | 156 строк | установка, таблица env, `--check-config`, запуск, ручная проверка, негативные сценарии |
| `test_link_handler.py` | +43/−211 | перевод на общий каркас вместо локальных копий |
| ревью ×2 + FIX | 137 шагов | handoff, дублирование каркаса, сканер секретов, шум в e2e |

Продакшн-кода — 1 строка. Тестовых файлов в работе — 6 (3 новых).
Сквозной тест проходит через все слои, поэтому его нельзя написать «в один
файл»: нужен общий каркас, а общий каркас надо вынести и перевести на него
старый тест — иначе ревью записывает P2 за дублирование (так и вышло).

## Почему это системно, а не разово

Тот же механизм был виден раньше, но маскировался продакшн-кодом:

- **T-007** (S, 106 шагов): 145 строк продакшна, но 5 тестовых файлов и
  27 кейсов — стоимость в тестовой обвязке;
- **T-008** (S, 178 шагов): 335 строк продакшна при 413 строках тестов и
  двух раундах ревью;
- **T-009** (S, 178 шагов): 1 строка продакшна при 662 строках тестов,
  156 строках README и двух раундах ревью.

Во всех трёх случаях ярлык S ставился по ощущению «это же не фича», а
поверхность (файлы, слои, проверки) была как у M. T-009 — чистый эксперимент:
кода нет вообще, а цена та же. Значит, **цена задачи пропорциональна не
строкам кода, а числу проверяемых контрактов**: шаблон заметки, порядок
сообщений, права доступа, тексты ошибок, README.

## Правило планирования

- **Тестовая/документационная задача оценивается как минимум M**, если в ней
  больше одного нового файла или сквозной сценарий через несколько слоёв.
  Формулировка «только тесты» не уменьшает размер.
- Считать поверхность: `новые тестовые файлы + изменённые тестовые файлы +
  сквозные кейсы + документы`. Три новых тестовых файла и README — это M с
  FIX-резервом.
- **Сквозной тест — отдельное слагаемое.** Он требует общего каркаса
  (`tests/support.py`), иначе дублирует фейки и получает P2 на ревью.
  Закладывать 10–20 шагов на вынос каркаса до написания самого E2E.
- **E2E требует `tmp_path`** (пишет заметку в `DATA_DIR`), поэтому в
  read-only песочнице ревьюера он не проходит. Либо предусмотреть
  read-only-путь (проверка чистых функций/рендера без файла), либо принять,
  что главный артефакт ревьюер воспроизводит вручную — это стоит 5–10 шагов
  и снижает доказательность (см. `reviewer-readonly-tests.md`).
- **README под тестами** — дешёвый способ удержать документацию от
  расхождения (23 проверки), но он добавляет ещё один файл и ещё один
  предмет ревью. Для проекта это оправдано: README — единственная инструкция
  запуска.

## Что не сработало

- Прогноз цикла 8 ждал дорогую реализацию (EXECUTE 50–70) и дешёвое ревью;
  факт — EXECUTE 41, ревью и исправления 137 шагов. Ошибка в структуре, а не
  в объёме: см. `cycle-09-spend.md`.
- Метка S в третий раз подряд не описала задачу: 106, 178 и 178 шагов у трёх
  «S». См. `estimate-size-s-collapsed-into-m.md`.
- E2E не включил кейсы P1-долга T-004/T-005 (пустой транскрипт,
  `InvalidURL`/`RuntimeError`) — значит, «сквозной сценарий» закрывает
  счастливый путь и известные ошибки, но не долг. См. `t009-review-issues.md`.

## Цикл 10: E2E + README стоит как кодовая M3

T-010 («сквозной текстовый сценарий шаблона и README») — второе подтверждение
на чистом классе: **105 шагов, 73,2 тыс. output, 14,20 млн токенов** — больше
любой кодовой задачи цикла, включая `/template` (72 шага) и проводку
(87). Диф: `test_template_e2e.py` 657 строк (9 кейсов через
`build_application`: сохранение, сброс, изоляция двух ID, перезапуск,
неподтверждённый кандидат, ошибка разбора, ссылка во время ввода, устаревшая
кнопка, ошибка записи), `test_readme.py` +105, README +82, `tests/support.py`
переиспользован (второго `Harness` нет).

Что это уточняет:

- README — самая дешёвая часть задачи (82 строки, 105 строк тестов), но
  тащит за собой ещё один предмет ревью; без него E2E-задача была бы
  ~90 шагов.
- Сквозной сценарий на **FSM** дороже, чем на stateless-обработчике T-009:
  нужно проверить порядок состояний, устаревшие кнопки и перезапуск, а не
  только «сообщение → файл».
- В read-only песочнице E2E не исполняется (`tmp_path`), поэтому цена
  проверки переносится на ревью вручную или на гейт VERIFY — см.
  `reviewer-readonly-tests.md`.
- Для прогноза: E2E + README — **M3 (80–115 шагов)** даже без продакшн-кода;
  тестовые строки (657) предсказывают шаги лучше, чем строки README (82).

## Цикл 12: тесты в 3,3 раза больше кода — 134 шага

T-012 (голосовой ввод) — третье подтверждение и самый чистый пример, потому
что продакшн-код был **меньше**, чем у предыдущей задачи, а шагов стало
больше: **134 EXECUTE, 99,1 тыс. output** против 90 и 45,7 тыс. у T-011.

- Продакшн — **347 строк** (обработчик +280, `bootstrap` +43, роутер +10,
  конфиг +9, адаптер +3, реэкспорт +2).
- Тесты — **1161 строка**: два новых файла (516 + 357) и четыре
  изменённых, включая `tests/support.py` (+152). Тестов в **3,3 раза**
  больше кода.
- README — +74, `.env.example` — +2.
- Полных прогонов набора — **6** (923 → 923 → 925 → 925 → 928 → 927
  passed), плюс целевые; тесты ни разу не были красными. Шаги ушли не на
  отладку, а на **написание** тестов и правки общего каркаса.

Что это уточняет:

- **`tests/support.py` — отдельное слагаемое.** 12 из 42 `edit` — правки
  каркаса (`FakeSpeechTranscriber`, аудио в `FakeSession`, поле `speech` в
  `TemplateStand`). Третья задача подряд (T-009, T-010, T-012), где общий
  каркас — главная статья расхода; его рост стоит закладывать в прогноз
  как 10–20 шагов.
- **E2E + README + юнит-тесты вместе — M4.** 5 сквозных кейсов (357 строк)
  и README (74) добавили ~40–50 шагов к «обычной» M; если задача ещё и
  закрывает долги, потолок M3 пробит (`estimate-m3-ceiling-broken.md`).
- **Ревью тоже платит за тесты:** 63 шага на 7 тестовых файлов (включая
  `support.py`) против 35 на 2 (T-011). Целевые unit-тесты в read-only
  прошли (15/15), E2E — нет (пишет `DATA_DIR`), т.е. цена проверки E2E
  остаётся за гейтом VERIFY.
- **Счёт тестов вести от `--collect-only`, а не от прошлого отчёта:**
  893 → 927 (+34) совпало с diffstat (15 + 5 + README/конфиг/проводка),
  но T-011 уже показала, что прошлый счёт может отставать на 4.

## Цикл 13: тесты вдвое больше продакшна, но шаги ушли в аудит

T-013: продакшн — 234 строки, тесты — 472 (+84 кейса) в четырёх
существующих файлах, новых тестовых файлов нет. 166 шагов EXECUTE — больше,
чем у T-012 (134), хотя строк тестов в 2,5 раза меньше (472 против 1161) и
новых файлов нет. Значит, шаги ушли не в тестовую обвязку, а в **чтение 13
источников долга и 46 прогонов гейтов**. Правило уточняется: при равном
объёме тестов новый файл дороже расширения существующего (T-012 vs T-013),
но аудит-задача может стоить больше и без новых тестов — считайте не только
тестовые файлы, но и число модулей/источников проверки
(`estimate-audit-task-cost.md`).
