# Задача без продакшн-кода стоит как M: T-009 дала 178 шагов и 154,7 тыс. output

Дата: 2026-11-26. T-009 формулировалась как «добавить сквозной тест и README»
и была помечена **S**. В диффе цикла — **одна строка продакшн-кода**
(версия в `tldw/__init__.py`), а расход — 178 шагов, 154,7 тыс. output и
11,82 млн токенов: больше, чем любая кодовая задача проекта. Причина не в
объёме, а в **ширине поверхности проверки** и в двух раундах ревью.

## Что именно стоило шагов

| Работа | Объём | Чем стоила |
|---|---|---|
| `tests/support.py` | 272 строки, новый | общий каркас: `Harness`, `make_harness`, `run_message`, фейковые источник/суммаризатор, константы видео |
| `tests/test_e2e.py` | 224 строки, 5 кейсов | настоящий `Dispatcher` → `LinkHandler` → `SummaryService` → `storage`; подменены только Telegram/YouTube/LLM |
| `tests/test_readme.py` | 118 строк, 23 проверки | README как исполняемый контракт: команды, все env-переменные, ручной сценарий, сканер секретов по `app/**/*.py` |
| `app/README.md` | 156 строк | установка, таблица env, `--check-config`, запуск, ручная проверка, негативные сценарии |
| `test_link_handler.py` | +43/−211 | перевод на общий каркас вместо локальных копий |
| ревью ×2 + FIX | 137 шагов | handoff, дублирование каркаса, сканер секретов, шум в e2e |

Продакшн-кода — 1 строка. Тестовых файлов в работе — 6 (3 новых).
Сквозной тест проходит через все слои, поэтому его нельзя написать «в один
файл»: нужен общий каркас, а общий каркас надо вынести и перевести на него
старый тест — иначе ревью записывает P2 за дублирование (так и вышло).

## Почему это системно, а не разово

Тот же механизм был виден раньше, но маскировался продакшн-кодом:

- **T-007** (S, 106 шагов): 145 строк продакшна, но 5 тестовых файлов и
  27 кейсов — стоимость в тестовой обвязке;
- **T-008** (S, 178 шагов): 335 строк продакшна при 413 строках тестов и
  двух раундах ревью;
- **T-009** (S, 178 шагов): 1 строка продакшна при 662 строках тестов,
  156 строках README и двух раундах ревью.

Во всех трёх случаях ярлык S ставился по ощущению «это же не фича», а
поверхность (файлы, слои, проверки) была как у M. T-009 — чистый эксперимент:
кода нет вообще, а цена та же. Значит, **цена задачи пропорциональна не
строкам кода, а числу проверяемых контрактов**: шаблон заметки, порядок
сообщений, права доступа, тексты ошибок, README.

## Правило планирования

- **Тестовая/документационная задача оценивается как минимум M**, если в ней
  больше одного нового файла или сквозной сценарий через несколько слоёв.
  Формулировка «только тесты» не уменьшает размер.
- Считать поверхность: `новые тестовые файлы + изменённые тестовые файлы +
  сквозные кейсы + документы`. Три новых тестовых файла и README — это M с
  FIX-резервом.
- **Сквозной тест — отдельное слагаемое.** Он требует общего каркаса
  (`tests/support.py`), иначе дублирует фейки и получает P2 на ревью.
  Закладывать 10–20 шагов на вынос каркаса до написания самого E2E.
- **E2E требует `tmp_path`** (пишет заметку в `DATA_DIR`), поэтому в
  read-only песочнице ревьюера он не проходит. Либо предусмотреть
  read-only-путь (проверка чистых функций/рендера без файла), либо принять,
  что главный артефакт ревьюер воспроизводит вручную — это стоит 5–10 шагов
  и снижает доказательность (см. `reviewer-readonly-tests.md`).
- **README под тестами** — дешёвый способ удержать документацию от
  расхождения (23 проверки), но он добавляет ещё один файл и ещё один
  предмет ревью. Для проекта это оправдано: README — единственная инструкция
  запуска.
