# Git в DSH-сессиях сломан двумя переменными окружения

Дата: 2026-11-26. Наблюдение по циклам 1–4: практически каждая сессия
(developer, reviewer, analyst) тратит первые шаги на две одинаковые ошибки git.
Это не дефект проекта, а окружение харнесса, но оно систематически съедает
шаги и внимание агентов.

## Симптом 1: битый `GIT_CONFIG_*`

```
error: missing config key GIT_CONFIG_KEY_0
fatal: unable to parse command-line config
```

В окружении стоит `GIT_CONFIG_COUNT=1` и `GIT_CONFIG_VALUE_0=/workspace`, но
`GIT_CONFIG_KEY_0` отсутствует. Git пытается прочитать конфиг из переменных и
падает ещё до команды. Лечение — убрать эти переменные для вызова:

```bash
env -u GIT_CONFIG_COUNT -u GIT_CONFIG_VALUE_0 -u GIT_CONFIG_KEY_0 git status
```

## Симптом 2: `dubious ownership`

```
fatal: detected dubious ownership in repository at '/workspace'
```

Репозиторий принадлежит другому uid, чем процесс агента. Лечение — one-shot
исключение, без правки глобального конфига:

```bash
git -c safe.directory=/workspace status
```

## Рабочая обёртка

Обе проблемы встречаются вместе, поэтому удобнее функция на сессию:

```bash
git_ws() {
  env -u GIT_CONFIG_COUNT -u GIT_CONFIG_VALUE_0 -u GIT_CONFIG_KEY_0 \
    git -c safe.directory=/workspace "$@"
}

git_ws status --porcelain -uall
git_ws --no-pager diff --stat e82aef6
git_ws --no-pager log --oneline -5
```

- Не пытайтесь «починить» окружение, задав `GIT_CONFIG_KEY_0`: переменные
  приходят из харнесса, их набор может меняться. Надёжнее отключить их на
  время вызова.
- Не добавляйте `safe.directory` в глобальный конфиг и не меняйте `.git/config`:
  это общая копия репозитория, а не ваша.
- После обёртки проверяйте `exit code`; пустой вывод `git status` — это норма,
  а не ошибка.

## Цена

- Цикл 3, developer: ~10 вызовов на диагностику и обход git до и во время
  работы; reviewer: первые ~15 из 40 вызовов инструментов.
- Цикл 4: developer сразу использовал `git_ws` и потратил на git 7 вызовов
  без диагностики; reviewer снова начал с `git status`, получил обе ошибки и
  потратил 5 из 48 вызовов на обход, прежде чем перейти к диффу.
- Циклы 1–2: та же картина в каждой сессии; в цикле 2 разработчик и ревьюер
  независимо нашли `env -u GIT_CONFIG_COUNT -u GIT_CONFIG_VALUE_0`.
- Цикл 5: developer сразу использовал `git_ws` — 7 вызовов на git, ни одной
  диагностики. Reviewer снова начал с `git status` без обёртки, получил
  `missing config key GIT_CONFIG_KEY_0`, и лечил его **не так, как в скиле**:
  `GIT_CONFIG_KEY_0=safe.directory git ...` — то есть задал недостающий ключ
  вручную. Это сработало в этой сессии, но противоречит рекомендации «снять
  переменные»: набор `GIT_CONFIG_*` приходит из харнесса и может измениться.
  На диагностику ушло 5 из 40 вызовов, что совпадает с циклом 4.
- Цикл 6: developer — 7 git-вызовов без диагностики; reviewer — 14 вызовов
  (обёртка + поиск untracked + `git diff HEAD`), потому что начал с обычного
  `git status` и `git diff`.
- Цикл 7: developer — 7 git-вызовов, reviewer — 10, оба через обёртку, без
  диагностики `GIT_CONFIG_*` и `dubious ownership`. Скил `git-in-sandbox`
  применяется с первого вызова.
- Итого **9 из 9 циклов**; у разработчика это 5–10 шагов (6–16 % задачи), у
  ревьюера — 5–15 вызовов. Инфраструктура, не связанная с продуктом, но она
  систематически съедает начало каждой сессии.

## Цикл 8 (T-008): 8 из 8, и по-прежнему не с первого вызова

В цикле 8 обёртка `git_ws` применялась после первой упавшей команды в каждой
из четырёх сессий: **7 упавших git-вызовов** (EXECUTE — 1, FIX — 1,
REVIEW-1 — 2, REVIEW-2 — 3) плюс `env | grep -i git` у второго ревьюера.
Типичный сценарий: сессия начинается с `git status`, получает
`missing config key GIT_CONFIG_KEY_0`, вспоминает про скил и дальше работает
через обёртку. Цена — 1–3 шага на сессию и лишний шум в логе. Правило не
изменилось: **первый git-вызов в любой роли — сразу через `git_ws`**; скил
`git-in-sandbox` читается до первой команды, а не после ошибки.

В цикле 5 проявился и второй git-сюрприз ревью: после `git add -N` изменения
уже в индексе, поэтому обычный `git diff` пуст — смотреть нужно `git diff HEAD`
или `git diff --cached` (см. `review-diff-untracked.md`). Это не сбой
окружения, но тоже стоит шагов, если не знать заранее.

## Цикл 9 (T-009): 9 из 9, шесть упавших вызовов

Обёртка снова применялась **после** первой ошибки в каждой сессии, где git
вообще вызывался: **6 упавших git-команд** (EXECUTE — 1 на шаге 30, REVIEW-1 —
2 на первом шаге, REVIEW-2 — 3, FIX — 0, потому что начал с чтения памяти и
скила). В EXECUTE после ошибки был прочитан `git-in-sandbox`, и дальше все
команды шли через обёртку. Цена — 1–2 шага на сессию и лишний шум в логе;
правило не изменилось: **первый git-вызов в любой роли — сразу через
`git_ws`**, скил читается до первой команды, а не после ошибки. В цикле 9
особенно заметно у ревьюера: обе сессии начались с `git status`/`git diff`
без обёртки, получили ошибку, и только потом перешли на `git diff HEAD`.

Паттерн вынесен в скил `app/skills/git-in-sandbox/SKILL.md`. Поскольку
`orchestrator/`, `dsh/` и `docker/` защищены, в LEARN меняются только память
и скил; чинить сам харнесс — отдельная задача типа `sdlc:`.

## Цикл 10: 18 упавших вызовов в 13 из 13 сессий — худший результат

В цикле 10 git вызывался в 13 сессиях из 14; **18 команд упали** на
`missing config key GIT_CONFIG_KEY_0` / `dubious ownership` — втрое больше
цикла 9 (6). Падения были во **всех 13 сессиях, где вызывался git**; intake
git не вызывал. Картина:

- ANALYZE — 2 падения, PLAN — 2 (обе сессии начали с `git log`/`git status`);
- каждый EXECUTE (10 из 10) — 1–2 падения: первая git-команда в сессии шла
  без обёртки, затем агент читал скил и переходил на `git_ws`;
- REVIEW — 2 падения: сначала обычный `git status`, затем
  `unset GIT_CONFIG_COUNT GIT_CONFIG_VALUE_0` без `-c safe.directory` — и
  только потом рабочая обёртка.

Суммарно 85 git-вызовов, из них 18 неудачных (21 %). Цена — 1–3 шага на
сессию и лишний шум; правило не изменилось: **первый git-вызов в любой роли —
сразу через `git_ws`**, скил `git-in-sandbox` читается до первой команды.
Батч-инкремент усилил проблему: сессий стало больше (14), и каждая
разработчик-сессия повторяла одну и ту же ошибку, потому что не видела
предыдущих.

Замечание для замера: фраза `missing config key GIT_CONFIG_KEY_0` встречается
в самой памяти, скилах и фактах, поэтому считать падения по вхождению строки
в вывод нельзя — только по `toolCallId` bash-вызова, в команде которого есть
`git`. Иначе счёт завышается в 1,5–2 раза (в этом LEARN первый подсчёт дал
28 вместо 18).

## Цикл 11: 4 упавших вызова, 11 из 11 — дешевле, потому что git реже

В цикле 11 git вызывался всего 12 раз (EXECUTE — 1, REVIEW — 11) против 85
в цикле 10. Разработчик сделал один обычный `git status` и не повторял;
ревьюер начал с трёх обычных `git status`/`git diff`/`git log`, получил
`GIT_CONFIG_KEY_0` и `dubious ownership`, затем перешёл на
`unset GIT_CONFIG_*` + `git -c safe.directory=/workspace`. Итого **4 упавших
вызова** — меньше 18 не потому, что окружение починили, а потому, что
одиночный цикл реже обращается к git. Правило не изменилось: **первый
git-вызов в любой роли — сразу через `git_ws`**; в цикле 11 обёртка снова
не была первым вызовом. Итог: **11 из 11 циклов** с этой инфраструктурной
проблемой.
