# Расход цикла 11: одиночная M3 — адаптер распознавания речи (T-011)

Дата: 2026-11-27. Цикл 11 — первый цикл после батча 002. «Текущий инкремент»
был пуст, поэтому оркестратор поднял из бэклога **одну** задачу T-011
(адаптер распознавания речи, метка **M**). Подготовки не было: новых
коммитов, черновиков и отчёта о сбое нет, ANALYZE/PLAN пропущены. Цикл

## Сравнение с оценкой

T-011 помечена **M**, без подкласса и без прогноза: задача лежала в бэклоге
с этой меткой, ANALYZE не запускался.

- **EXECUTE 90** попадает в **M3 (80–115)**, ближе к нижней половине;
  **REVIEW 35** — в вилку 25–40; итог **125** — в прогноз
  `M3 + REVIEW = 105–155`. Output 81,3 тыс. — в M3 65–95 тыс.; токены
  9,87 млн — между M2 и M3;
- **плоская M** (`55–70 + 25–40 = 80–110`) промахнулась бы в
  **1,14–1,56 раза**; один EXECUTE (90 против 55–70) — в 1,29–1,64 раза.
  Старое правило «M с новой внешней интеграцией: 80–120 шагов» даёт
  125 против 120, то есть +4 %;
- тот же класс, что T-004 (LLM-адаптер, M, 60 шагов EXECUTE), стоит на
  **50 % дороже**: T-011 добавил не только адаптер, но и конфиг, env,
  README и 52 теста, а разработчик потратил 16 прогонов гейтов. Это ещё
  один довод, что «M» без подкласса — не прогноз; см.
  `estimate-backlog-label-stale.md` и `estimate-m-bucket-wide.md`;
- по сравнению с циклом 10 **на задачу**: 125 против 88,1 шага (+42 %),
  81,3 против 77,3 тыс. output (+5 %), 9,87 против 9,36 млн токенов
  (+5,5 %), 19,6 против ≈12 мин (+63 %); ревью — 35 против 5,6 шага
  (в 6,25 раза больше), зато оно прогнало 685 тестов из 893 (77 %) и нашло
  два P2, а батч-ревью — 158 из 828 (19 %) и отложило восемь пунктов.
  Это цена «полной проверки одной задачи», разрешённая ADR-014; см.
  `single-task-pull-from-backlog.md`.

## Куда ушли шаги

- **Разработка нового адаптера, а не исследование API.** 33,7 % вызовов до
  первой правки — это чтение `llm.py` (образец), `errors.py`, `config.py`,
  `support.py` и тестов; сам API знаком. Основная цена — 331 строка
  адаптера, 410 строк тестов, 4 опциональные env, README и 16 прогонов
  гейтов.
- **Ревью — reasoning-heavy.** 35 шагов, но 35,6 тыс. output (1 018 на шаг)
  и 41 `bash`: ревьюер прогнал целевые файлы, полный набор, `ruff`,
  проверил границы `app/`, `specs/`, секреты и воспроизвёл `InvalidURL`.
  Output ревью — 78 % от output разработчика при 39 % шагов.
- **Git-окружение снова сломано, но дешевле.** Ревьюер начал с обычных
  `git status`/`git diff`, получил `GIT_CONFIG_KEY_0`/`dubious ownership` и
  перешёл на `unset GIT_CONFIG_*` + `git -c safe.directory=/workspace`;
  разработчик сделал один обычный `git status`. Всего ≈4 упавших вызова из
  12 — меньше, чем 18 в цикле 10, потому что git вызывался реже; см.
  `git-env-broken-in-dsh.md`.

## Что это значит для следующего цикла

- **Одна задача — не «дешёвый цикл».** 125 шагов и 19,6 мин на одну M;
  на задачу это +42 % к батчу, но ревью реально исполняет тесты и находит
  дефекты. Для нового внешнего адаптера или поведения безопасности это
  оправданный режим (ADR-014 его не запрещает), для механических задач —
  нет.
- **T-012 (голосовой ввод в Telegram) — M3, а не M.** Ей нужны обработчик,
  allowlist до скачивания/распознавания, `to_thread`, FSM, E2E и README;
  прогноз — `EXECUTE 80–115 + REVIEW 25–40 = 105–155` шагов, 65–95 тыс.
  output, с риском FIX, если ревью вернёт `ISSUES`.
- **Долг вырос на 6 групп** (2 P2 + 4 P3), FIX не было: 77 → **83** пункта;
  P1 T-004/T-005 по-прежнему открыты, а `InvalidURL` повторился в новом
  адаптере (`invalidurl-escapes-every-adapter.md`,
  `t011-review-issues.md`).
- **Handoff снова сломан:** `git add -N` не выполнен, 741 строка вне
  diffstat; это третья регрессия после T-006 и T-009. Правило
  `review-handoff` остаётся обязательным шагом, а не «хорошей практикой».
