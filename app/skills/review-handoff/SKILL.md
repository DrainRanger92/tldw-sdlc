## Когда применять

- Перед финальным ответом в любой задаче, где появились новые файлы.
- При чтении отчёта ревьюера: понять, что он реально мог проверить.
- При подготовке промпта ревью: какие флаги и какая база диффа нужны.

## Сначала — рабочая git-обёртка

В DSH-сессиях git сломан двумя переменными окружения
(`missing config key GIT_CONFIG_KEY_0` и `dubious ownership`). Не тратьте шаги
на диагностику — используйте обёртку из `app/skills/git-in-sandbox/SKILL.md`:

```bash
git_ws() {
  env -u GIT_CONFIG_COUNT -u GIT_CONFIG_VALUE_0 -u GIT_CONFIG_KEY_0 \
    git -c safe.directory=/workspace "$@"
}
```

## Подготовка рабочей копии

```bash
cd /workspace
git_ws add -N app/                 # intent-to-add: новые файлы попадают в git diff
git_ws status --porcelain -uall    # полный список untracked
git_ws diff --stat <base>
git_ws diff <base> -- app/
```

- `git add -N` не коммитит содержимое, но делает новые файлы видимыми в
  `git diff`; без него diffstat может показать только правку `__init__.py`
  (цикл 6: 109 строк вместо ~721). Выполняйте его **до** подсчёта diffstat.
- Если после `add -N` появился ещё один новый файл, повторите `add -N` для
  него.
- Сверьте каждый путь из `git status -uall` с диффом. Если файл есть в
  статусе, но не в диффе — ревьюер его не увидит, пока не прочитает вручную.
- Не считайте `git diff --stat` полным описанием изменения, пока в рабочей
  копии есть untracked-файлы. Если diffstat меньше ожидаемого объёма новых
  файлов — handoff сломан, а не «кода мало».
- Оркестратор коммитит через `git add -A`, поэтому код не потеряется, но
  ревью должно видеть его до коммита.
- **Регрессия цикла 9:** `git add -N` забыли именно потому, что новые файлы —
  тесты и README, а не «настоящий» модуль. Правило не зависит от типа файлов:
  появился новый `.py`/`.md` в `app/` — `add -N` до diffstat.
- **После `git add -N` обычный `git diff` у ревьюера пуст** — изменения уже в
  индексе. В цикле 5 ревьюер потратил на это шаги: смотреть нужно
  `git diff HEAD <base>` (или `git diff --cached <base>`). Это стоит писать в
  промпте ревью явно: «рабочая копия подготовлена через `git add -N`, база —
  коммит `<sha>`, смотри `git diff HEAD <sha>`».

## Что ревьюер может проверить в read-only песочнице

- Запись в `/tmp` недоступна: тесты с `tmp_path` падают с
  `FileNotFoundError: No usable temporary directory`. Это ограничение
  окружения, а не дефект кода; не требовать исправления.
- В цикле 5 `pytest` без флагов падал ещё до сбора тестов — в
  `_pytest/capture.py` при создании временного файла для перехвата вывода.
  В цикле 6 без флагов он тоже не собирался. Рабочий обход — отключить
  capture и кэш:

```bash
cd /workspace/app
PYTHONDONTWRITEBYTECODE=1 .venv/bin/python -m pytest -q -p no:cacheprovider -s
.venv/bin/ruff check --no-cache .
```

- Тесты без `tmp_path` пройдут; тесты с ним — ошибки окружения. Динамика:
  цикл 1 — 12 passed + 46 env-errors, цикл 2 — 57 passed + 1 env-error,
  цикл 3 — 116 passed + 47 env-errors, цикл 4 — полный прогон недоступен,
  `test_llm_adapter.py` — 48 passed, цикл 5 — 16 passed + 29 env-errors,
  цикл 6 — 198 passed + 84 env-errors из 282 тестов, цикл 7 — 34 passed +
  9 env-errors (`test_access.py` целиком + не-`tmp_path` кейсы
  `test_link_handler.py`) и 5 passed + 52 env-errors в
  `test_config`/`test_bootstrap`/`test_cli` из 309, цикл 8 — **243 passed +
  93 env-errors из 343** (целевые `test_errors.py` и новые кейсы
  `test_link_handler.py` — 27 passed до исправлений и 26 + 9 после). Число
  ошибок зависит от доли тестов, которым нужен временный каталог; это не
  регрессия.
- В цикле 3 новый `test_youtube_adapter.py` не использует `tmp_path` и прошёл
  отдельно: 47 passed. В цикле 4 так же прошёл `test_llm_adapter.py`
  (48 passed). Если новый модуль не трогает файловую систему, его можно
  прогнать целиком даже в read-only. Для сервисных тестов (цикл 5) проверяйте
  чистые функции напрямую — `join_transcript`, `build_note`, `parse_summary`:
  они не пишут файлов и дают проверяемое поведение без `tmp_path`. В цикле 6
  из `test_link_handler.py` прошли 13 кейсов из 21 — ровно те, что не пишут
  файлы; сценарный кейс с настоящим `SummaryService` требует `tmp_path`.
  В цикле 7 `test_access.py` (15 кейсов, чистая политика) прошёл целиком, а
  из `test_link_handler.py` — 19 из 28; для задач с чистыми правилами это
  лучший первый прогон в read-only.
- `ruff check .` в read-only работает (лучше с `--no-cache`).
- Ревьюер T-004 потратил 5 вызовов на попытки прогнать полный `pytest`
  (`/tmp`, `/var/tmp`, `/dev/shm`, `TMPDIR`); не повторяйте эту диагностику —
  сразу проверяйте `ls -ld /tmp`, запускайте целевой файл или используйте
  `-p no:cacheprovider -s`.

## Граница `specs/`

В рабочей копии перед ревью часто изменён `specs/*/tasks.md`: оркестратор
переносит задачу из бэклога и ставит статус. Разработчик этих правок не
делает. Ревьюеру стоит явно сказать, какие изменения `specs/` принадлежат
оркестратору, иначе он потратит шаги на ложное «нарушение границы» (так было
в цикле 4). Проверять нужно только то, что разработчик не менял код задач и
не правил защищённые пути.

**Правка `specs/` в диффе — 4 из 4 последних циклов** (T-004, T-007, T-008,
T-009). В цикле 8 разработчик на FIX откатил её
`git checkout -- specs/001-mvp/tasks.md`, чтобы дифф был только про `app/`;
в цикле 9 FIX её оставил, сославшись на это правило. Правка не потерялась ни
там, ни там, но откат стоил шага и создал два противоположных прецедента.
Правило: **`specs/` в диффе — не дефект и не повод для отката**; называйте её
правкой оркестратора в ответе и в промпте ревью: «изменения `specs/` сделаны
оркестратором, проверяй только код и защищённые пути». Разработчику не нужно
«чистить» чужую правку перед ревью.

## Проверяйте тесты, а не только код

Цикл 8 — первый `ISSUES`: два дефекта критерия «в логе нет секретов» прошли
**27 зелёных тестов**. Причина — фикстура подходила под другой шаблон
(`sk-…` вместо `Bearer`), а многострочность проверялась без отступов.
Ревьюер нашёл оба дефекта ручным воспроизведением формы из реального кода
(`llm.py`: `Authorization: Bearer …`), а не запуском тестов.

Что делать ревьюеру:

- брать входы **из работающего кода**, а не из тестов: формат заголовка,
  форма транскрипта, repr исключения;
- проверять **мутацией**: если убрать проверяемую ветку/шаблон, тест должен
  упасть; если не падает — тест проверяет не то;
- проверять обе стороны очистки: секрет вырезан **и** похожий не-секрет
  (`max_tokens=4096`) не тронут;
- писать в отчёте, что именно проверено вручную: это отличает «прочитал
  дифф» от «воспроизвёл дефект» (T-008: 23 шага, 11,8 тыс. output — дешевле
  любого `APPROVE`-прохода циклов 4–7).

## Разделяйте два факта

«Ревьюер прочитал код и сказал APPROVE» ≠ «pytest зелёный». Полный прогон
делает детерминированный гейт VERIFY в обычной песочнице; в отчёте цикла эти
два результата не смешивать. Если ревьюер пишет про ошибки `tmp_path`,
проверьте, что они не попали в список дефектов.

В цикле 3 ревью дало `APPROVE` с первой итерации, но 10 неблокирующих
замечаний (P1 — таймаут основного источника, двойной `_extract_info`,
приоритет ошибок). В цикле 4 — `APPROVE`, 40 шагов и 7 групп замечаний,
включая поведенческую дыру `httpx.InvalidURL` мимо `LLMError`. В цикле 5 —
`APPROVE`, 28 шагов, 8 пунктов, включая незакрытый пустой транскрипт. В
цикле 6 — `APPROVE`, 39 шагов, 9 пунктов: P2 за untracked-дифф, P3 за URL в
логе, границу `_LINK_RE`, отсутствие отмены фоновых задач и лимита
параллелизма. В цикле 7 — `APPROVE`, 36 шагов, 6 пунктов: P2 за fail-open
default и незащищённый отказ, P3 за дубль дедупликации ID, хрупкие проверки
логов и неточную версию в CHANGELOG. **В цикле 8 — `ISSUES`, 23 шага, 6
пунктов, два из них — реальные дефекты безопасности логов;** после FIX
второй проход — `APPROVE`, 52 шага, 1 P2 и 4 P3. **В цикле 9 — снова
`ISSUES`, 28 шагов, 7 групп, но ни одного дефекта поведения:** оба P2 —
процессные (untracked-файлы и дублированный тестовый каркас). После FIX
второй проход — `APPROVE`, 60 шагов, 3 P3. APPROVE не означает «долга
нет»: см. `app/memory/facts/review-debt-accumulates.md`. Бюджет ревью
считайте от диффа, handoff и числа тестовых файлов: для ~1 100–1 200 строк и
8–9 файлов — 25–40 шагов и 16–42 тыс. output; для ~700 строк и 9 файлов — 30–40
шагов и 20–32 тыс.; для ~450 строк, но 5 тестовых файлов (T-007) — 30–40
шагов и 18–25 тыс.; для ~730 строк и 2 тестовых файлов (T-008) первый проход
— 20–30 шагов и 10–15 тыс., **второй — 45–55 шагов и 45–50 тыс.**; для
~836 строк и 6 тестовых файлов (T-009) — 28 шагов и 23,7 тыс., **второй —
60 шагов и 49,0 тыс.**; плюс 5–10 шагов, если новые файлы не попали в дифф.
Доля — 0,4–0,9 шага на шаг разработчика в циклах без возврата (в цикле 5 —
0,42, в цикле 6 — 0,63, в цикле 7 — 0,51) и 1,5–2,2 при двух раундах
(T-008: 1,56; T-009: 2,15).

- [ ] `git add -N app/` выполнен, если появились новые файлы (до diffstat);

- [ ] `git status --porcelain -uall` сверен с `git diff --stat`; если
      diffstat меньше ожидаемого — handoff сломан, файлы названы в ответе.
- [ ] В дифф попал каждый новый файл (или он явно назван в ответе).
- [ ] В промпте ревью указано смотреть `git diff HEAD <base>`, а не `git diff`.
- [ ] Полный `pytest -q` прогнан в обычной песочнице разработчика.
- [ ] Ошибки `tmp_path` у ревьюера не записаны как дефекты кода.
- [ ] Число тестовых файлов и новых кейсов названо в ответе: оно предсказывает
      шаги ревью лучше, чем размер диффа.
