## Когда применять

- Перед финальным ответом в любой задаче, где появились новые файлы.
- При чтении отчёта ревьюера: понять, что он реально мог проверить.
- При подготовке промпта ревью: какие флаги и какая база диффа нужны.

## Сначала — рабочая git-обёртка

В DSH-сессиях git сломан двумя переменными окружения
(`missing config key GIT_CONFIG_KEY_0` и `dubious ownership`). Не тратьте шаги
на диагностику — используйте обёртку из `app/skills/git-in-sandbox/SKILL.md`:

```bash
git_ws() {
  env -u GIT_CONFIG_COUNT -u GIT_CONFIG_VALUE_0 -u GIT_CONFIG_KEY_0 \
    git -c safe.directory=/workspace "$@"
}
```

## Подготовка рабочей копии

```bash
cd /workspace
git_ws add -N app/                 # intent-to-add: новые файлы попадают в git diff
git_ws status --porcelain -uall    # полный список untracked
git_ws diff --stat <base>
git_ws diff <base> -- app/
```

- `git add -N` не коммитит содержимое, но делает новые файлы видимыми в
  `git diff`; без него diffstat может показать только правку `__init__.py`
  (цикл 6: 109 строк вместо ~721). Выполняйте его **до** подсчёта diffstat.
- Если после `add -N` появился ещё один новый файл, повторите `add -N` для
  него.
- Сверьте каждый путь из `git status -uall` с диффом. Если файл есть в
  статусе, но не в диффе — ревьюер его не увидит, пока не прочитает вручную.
- Не считайте `git diff --stat` полным описанием изменения, пока в рабочей
  копии есть untracked-файлы. Если diffstat меньше ожидаемого объёма новых
  файлов — handoff сломан, а не «кода мало».
- Оркестратор коммитит через `git add -A`, поэтому код не потеряется, но
  ревью должно видеть его до коммита.
- **Регрессия цикла 9:** `git add -N` забыли именно потому, что новые файлы —
  тесты и README, а не «настоящий» модуль. Правило не зависит от типа файлов:
  появился новый `.py`/`.md` в `app/` — `add -N` до diffstat.
- **После `git add -N` обычный `git diff` у ревьюера пуст** — изменения уже в
  индексе. В цикле 5 ревьюер потратил на это шаги: смотреть нужно
  `git diff HEAD <base>` (или `git diff --cached <base>`). Это стоит писать в
  промпте ревью явно: «рабочая копия подготовлена через `git add -N`, база —
  коммит `<sha>`, смотри `git diff HEAD <sha>`».

## Батч-ревью: один проход на N задач

Если инкремент содержит несколько задач, ревьюер получает один diffstat и
один список `T-001, T-002, …`. Что делать иначе, чем в одно-задачном цикле:

- **Проверять покрытие, а не только код.** Прочитать дифф целиком по
  модулям, но отдельно назвать, какие тестовые файлы реально исполнены.
  В цикле 10: `ruff` и AST — ок, 158 тестов без фикстур — passed, но
  `test_storage_templates.py`, `test_summary_templates.py`,
  `test_template_e2e.py` (главные артефакты T-002 и T-010) не запускались.
  В отчёте писать «158 из 828» (батч) или «685 из 893» (одиночный цикл 11),
  а не «тесты зелёные».
- **Сверять каждый набор критериев с задачей, а не дифф целиком.** При
  десяти задачах легко проверить сквозной сценарий и пропустить лимиты или
  изоляцию; выпишите T-001…T-010 и отметьте, чем каждая подтверждена.
- **Искать сквозные расхождения между задачами.** Батч-ревью сильно именно
  этим: в цикле 10 найдены формат «Таймкодов»/«Цитат» в динамическом пути,
  дубли валидаторов, второй источник лимитов и неверный текст ошибки —
  то, что при десяти независимых ревью могло остаться незамеченным.
- **`APPROVE` не закрывает долг.** Восемь замечаний цикла 10 остались без
  FIX; выпишите их отдельным файлом (`t001-t010-review-issues.md`) и
  назовите кандидатами в следующий инкремент.
- **Не требовать полного `pytest` от read-only.** Ошибки `tmp_path` —
  окружение; но и не писать «проверено всё». Полный прогон — гейт VERIFY
  (893 passed).

## Граница `specs/`

В рабочей копии перед ревью часто изменён `specs/*/tasks.md`: оркестратор
переносит задачу из бэклога и ставит статус. Разработчик этих правок не
делает. Ревьюеру стоит явно сказать, какие изменения `specs/` принадлежат
оркестратору, иначе он потратит шаги на ложное «нарушение границы» (так было
в цикле 4). Проверять нужно только то, что разработчик не менял код задач и
не правил защищённые пути.

**Правка `specs/` в диффе — 7 циклов: T-004 и T-007–T-012** (в цикле 10 —
`specs/001-mvp/plan.md` и удаление `D-001`; в цикле 11 — перенос T-011 из
бэклога в `specs/002-user-note-templates/tasks.md`; в цикле 12 — тот же
перенос для T-012, ±6 строк). В цикле 8 разработчик на FIX откатил её
`git checkout -- specs/001-mvp/tasks.md`, чтобы дифф был только про `app/`;
в цикле 9 FIX её оставил, сославшись на это правило. Правка не потерялась ни
там, ни там, но откат стоил шага и создал два противоположных прецедента.
Правило: **`specs/` в диффе — не дефект и не повод для отката**; называйте её
правкой оркестратора в ответе и в промпте ревью: «изменения `specs/` сделаны
оркестратором, проверяй только код и защищённые пути». Разработчику не нужно
«чистить» чужую правку перед ревью. Если ревьюер сомневается, отличать
артефакт от нарушения за один шаг: `git show <base> -- specs/` покажет тот же
паттерн в предыдущем коммите (`review-spec-edit-artifact.md`).

## Проверяйте тесты, а не только код

Цикл 8 — первый `ISSUES`: два дефекта критерия «в логе нет секретов» прошли
**27 зелёных тестов**. Причина — фикстура подходила под другой шаблон
(`sk-…` вместо `Bearer`), а многострочность проверялась без отступов.
Ревьюер нашёл оба дефекта ручным воспроизведением формы из реального кода
(`llm.py`: `Authorization: Bearer …`), а не запуском тестов.

Что делать ревьюеру:

- брать входы **из работающего кода**, а не из тестов: формат заголовка,
  форма транскрипта, repr исключения;
- проверять **мутацией**: если убрать проверяемую ветку/шаблон, тест должен
  упасть; если не падает — тест проверяет не то;
- проверять обе стороны очистки: секрет вырезан **и** похожий не-секрет
  (`max_tokens=4096`) не тронут;
- писать в отчёте, что именно проверено вручную: это отличает «прочитал
  дифф» от «воспроизвёл дефект» (T-008: 23 шага, 11,8 тыс. output — дешевле
  любого `APPROVE`-прохода циклов 4–7).

## Разделяйте два факта

«Ревьюер прочитал код и сказал APPROVE» ≠ «pytest зелёный». Полный прогон
делает детерминированный гейт VERIFY в обычной песочнице; в отчёте цикла эти
два результата не смешивать. Если ревьюер пишет про ошибки `tmp_path`,
проверьте, что они не попали в список дефектов.
