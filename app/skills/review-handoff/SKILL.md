# Передача изменений на ревью

Паттерн повторялся в циклах 1–5. В циклах 1 и 2 ревьюер получал
`git diff --stat`, в котором не было новых файлов: в цикле 1 — весь каркас
`app/`, в цикле 2 — `note.py` и `test_note.py`. В циклах 3–5 `git add -N`
сработал: ревьюер увидел все пути из `git status -uall`, совпавшие с
diffstat. Второй повтор — read-only песочница ревьюера: `tmp_path` падает
ошибкой окружения, а не дефектом кода; в цикле 3 это дало 47 env-errors, в
цикле 4 полный прогон не удался, но новый файл прошёл отдельно (48 passed), в
цикле 5 `pytest` упал ещё в capture, после флагов — 16 passed + 29 env-errors.

## Когда применять

- Перед финальным ответом в любой задаче, где появились новые файлы.
- При чтении отчёта ревьюера: понять, что он реально мог проверить.
- При подготовке промпта ревью: какие флаги и какая база диффа нужны.

## Сначала — рабочая git-обёртка

В DSH-сессиях git сломан двумя переменными окружения
(`missing config key GIT_CONFIG_KEY_0` и `dubious ownership`). Не тратьте шаги
на диагностику — используйте обёртку из `app/skills/git-in-sandbox/SKILL.md`:

```bash
git_ws() {
  env -u GIT_CONFIG_COUNT -u GIT_CONFIG_VALUE_0 -u GIT_CONFIG_KEY_0 \
    git -c safe.directory=/workspace "$@"
}
```

## Подготовка рабочей копии

```bash
cd /workspace
git_ws add -N app/                 # intent-to-add: новые файлы попадают в git diff
git_ws status --porcelain -uall    # полный список untracked
git_ws diff --stat <base>
git_ws diff <base> -- app/
```

- `git add -N` не коммитит содержимое, но делает новые файлы видимыми в
  `git diff`; без него diffstat может показать только правку `__init__.py`.
- Если после `add -N` появился ещё один новый файл, повторите `add -N` для
  него.
- Сверьте каждый путь из `git status -uall` с диффом. Если файл есть в
  статусе, но не в диффе — ревьюер его не увидит, пока не прочитает вручную.
- Не считайте `git diff --stat` полным описанием изменения, пока в рабочей
  копии есть untracked-файлы.
- Оркестратор коммитит через `git add -A`, поэтому код не потеряется, но
  ревью должно видеть его до коммита.
- **После `git add -N` обычный `git diff` у ревьюера пуст** — изменения уже в
  индексе. В цикле 5 ревьюер потратил на это шаги: смотреть нужно
  `git diff HEAD <base>` (или `git diff --cached <base>`). Это стоит писать в
  промпте ревью явно: «рабочая копия подготовлена через `git add -N`, база —
  коммит `<sha>`, смотри `git diff HEAD <sha>`».

## Что ревьюер может проверить в read-only песочнице

- Запись в `/tmp` недоступна: тесты с `tmp_path` падают с
  `FileNotFoundError: No usable temporary directory`. Это ограничение
  окружения, а не дефект кода; не требовать исправления.
- В цикле 5 `pytest` без флагов падал ещё до сбора тестов — в
  `_pytest/capture.py` при создании временного файла для перехвата вывода.
  Рабочий обход — отключить capture и кэш:

```bash
cd /workspace/app
PYTHONDONTWRITEBYTECODE=1 .venv/bin/python -m pytest -q -p no:cacheprovider -s
.venv/bin/ruff check --no-cache .
```

- Тесты без `tmp_path` пройдут; тесты с ним — ошибки окружения. Динамика:
  цикл 1 — 12 passed + 46 env-errors, цикл 2 — 57 passed + 1 env-error,
  цикл 3 — 116 passed + 47 env-errors, цикл 4 — полный прогон недоступен,
  `test_llm_adapter.py` — 48 passed, цикл 5 — 16 passed + 29 env-errors
  (весь набор — 257, из них 45 новых кейсов пишут файлы). Число ошибок
  зависит от доли тестов, которым нужен временный каталог; это не регрессия.
- В цикле 3 новый `test_youtube_adapter.py` не использует `tmp_path` и прошёл
  отдельно: 47 passed. В цикле 4 так же прошёл `test_llm_adapter.py`
  (48 passed). Если новый модуль не трогает файловую систему, его можно
  прогнать целиком даже в read-only. Для сервисных тестов (цикл 5) проверяйте
  чистые функции напрямую — `join_transcript`, `build_note`, `parse_summary`:
  они не пишут файлов и дают проверяемое поведение без `tmp_path`.
- `ruff check .` в read-only работает (лучше с `--no-cache`).
- Ревьюер T-004 потратил 5 вызовов на попытки прогнать полный `pytest`
  (`/tmp`, `/var/tmp`, `/dev/shm`, `TMPDIR`); не повторяйте эту диагностику —
  сразу проверяйте `ls -ld /tmp`, запускайте целевой файл или используйте
  `-p no:cacheprovider -s`.

## Граница `specs/`

В рабочей копии перед ревью часто изменён `specs/*/tasks.md`: оркестратор
переносит задачу из бэклога и ставит статус. Разработчик этих правок не
делает. Ревьюеру стоит явно сказать, какие изменения `specs/` принадлежат
оркестратору, иначе он потратит шаги на ложное «нарушение границы» (так было
в цикле 4). Проверять нужно только то, что разработчик не менял код задач и
не правил защищённые пути.

## Разделяйте два факта

«Ревьюер прочитал код и сказал APPROVE» ≠ «pytest зелёный». Полный прогон
делает детерминированный гейт VERIFY в обычной песочнице; в отчёте цикла эти
два результата не смешивать. Если ревьюер пишет про ошибки `tmp_path`,
проверьте, что они не попали в список дефектов.

В цикле 3 ревью дало `APPROVE` с первой итерации, но 10 неблокирующих
замечаний (P1 — таймаут основного источника, двойной `_extract_info`,
приоритет ошибок). В цикле 4 — `APPROVE`, 40 шагов и 7 групп замечаний,
включая поведенческую дыру `httpx.InvalidURL` мимо `LLMError`. В цикле 5 —
`APPROVE`, 28 шагов, 8 пунктов, включая незакрытый пустой транскрипт.
APPROVE не означает «долга нет»: см.
`app/memory/facts/review-debt-accumulates.md`. Бюджет ревью считайте от
диффа: для ~1 100–1 200 строк и 8–9 файлов — 25–40 шагов и 16–42 тыс.
output; доля 0,4–0,9 шага на шаг разработчика (в цикле 5 — 0,42), но для
композиции готовых контрактов она ближе к нижней границе (25 % output).

## Чек-лист перед ответом

- [ ] Использована обёртка `git_ws` (или другой обход битого git-окружения).
- [ ] `git add -N app/` выполнен, если появились новые файлы.
- [ ] `git status --porcelain -uall` сверен с `git diff --stat`.
- [ ] В дифф попал каждый новый файл (или он явно назван в ответе).
- [ ] В промпте ревью указано смотреть `git diff HEAD <base>`, а не `git diff`.
- [ ] Полный `pytest -q` прогнан в обычной песочнице разработчика.
- [ ] Ошибки `tmp_path` у ревьюера не записаны как дефекты кода.
