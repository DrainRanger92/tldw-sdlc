# Git в песочнице DSH

Паттерн повторялся в циклах 1–14 в каждой сессии — у developer, reviewer и
analyst. Две независимые ошибки окружения валят git ещё до команды; в цикле 3
разработчик потратил на диагностику ~10 вызовов, ревьюер — первые ~15 из 40.
В цикле 4 разработчик сразу применил обёртку и потратил 7 вызовов на git без
диагностики, а ревьюер снова начал с `git status` и потерял 5 из 48 вызовов.
В цикле 5 картина та же: developer — 7 вызовов с обёрткой и без диагностики,
reviewer — 5 вызовов на обход. В цикле 6 — снова 6/6: developer потратил 7
git-вызовов без диагностики, reviewer — 14 вызовов (обёртка + поиск
untracked + `git diff HEAD`), потому что начал с обычного git и `git diff`.
В цикле 7 обёртка применялась с первого вызова: developer — 7 git-вызовов,
reviewer — 10, ни одной ошибки `GIT_CONFIG_*`/`dubious ownership`. В цикле 8
обёртка снова применялась после первой ошибки в каждой из четырёх сессий
(7 упавших вызовов); в цикле 9 — то же самое, 6 упавших вызовов (EXECUTE 1,
REVIEW-1 2, REVIEW-2 3, FIX 0). **В цикле 10 — 18 упавших вызовов в 13 из 13
сессий:** каждый EXECUTE-разработчик начинал с обычного `git status`,
получал ошибку и только потом читал этот скил; ANALYZE и PLAN — по 2
падения, ревью — 2 (вторая попытка была `unset GIT_CONFIG_COUNT` без
`-c safe.directory`). Это не дефект проекта, а харнесс, поэтому лечится
обёрткой, а не правкой репозитория. **В цикле 11 — 11 из 11 циклов и 4
упавших вызова из 12:** разработчик сделал один обычный `git status`,
ревьюер — три обычных `git status`/`git diff`/`git log`, получил
`GIT_CONFIG_KEY_0`/`dubious ownership` и только потом перешёл на
`unset GIT_CONFIG_*` + `git -c safe.directory=/workspace`. Меньше, чем 18 в
цикле 10, потому что git вызывался реже (12 раз против 85), а не потому,
что окружение починили.

Правило: **первый git-вызов в любой роли — сразу через `git_ws`**, не после
ошибки. Скил читается до первой команды, а не после `missing config key`.

**В цикле 12 — 2 упавших вызова из 23, и разработчик впервые был чист с
первого вызова:** 9 git-вызовов EXECUTE (`status`, `diff`, `add -N`,
`diff HEAD`) через `git_ws` — 0 падений. Ревьюер начал с обычного
`git -C /workspace …` (2 падения: `GIT_CONFIG_KEY_0`, затем `dubious
ownership`), после `export GIT_CONFIG_KEY_0=safe.directory` остальные 12
прошли. Это второй чистый EXECUTE после цикла 7 и лучший относительный
результат (8,7 % против 33 % в цикле 11 и 21 % в цикле 10).

**В цикле 13 — 10 падений из 44 (23 %), регресс к обычному уровню.**
ANALYZE — 6/21 (начал с `git log`/`git status`, перебрал
`env -u GIT_CONFIG_*` и `git -c safe.directory`), EXECUTE — 1/10,
REVIEW — 3/13 (первые три вызова). Разработчик снова не начал с `git_ws`,
хотя в цикле 12 это сработало. Вывод: правило «первый вызов — сразу
`git_ws`» не стало привычкой; цена — 10 шагов на цикл, но в трёх сессиях
подряд. В аудит-задачах git вызывается чаще (21 раз в ANALYZE), поэтому
падения заметнее.

## Когда применять

- Любая git-команда в `/workspace` из DSH-сессии.
- Особенно перед `git status`, `git diff`, `git add -N`, `git log` — то есть
  в начале и в конце каждой задачи.
- **В батч-цикле сессий больше** (в цикле 10 — 14): ошибка повторяется в
  каждой, потому что агенты не видят предыдущих. Скил читается до первой
  команды, а не после `missing config key`.

## Симптомы

```text
error: missing config key GIT_CONFIG_KEY_0
fatal: unable to parse command-line config
```

В окружении есть `GIT_CONFIG_COUNT=1` и `GIT_CONFIG_VALUE_0=/workspace`, но нет
`GIT_CONFIG_KEY_0`. Git падает при разборе своего конфига.

```text
fatal: detected dubious ownership in repository at '/workspace'
```

Репозиторий принадлежит другому uid, чем процесс агента.

## Обёртка

Одна функция на сессию снимает обе проблемы:

```bash
git_ws() {
  env -u GIT_CONFIG_COUNT -u GIT_CONFIG_VALUE_0 -u GIT_CONFIG_KEY_0 \
    git -c safe.directory=/workspace "$@"
}

git_ws status --porcelain -uall
git_ws --no-pager diff --stat e82aef6
git_ws --no-pager log --oneline -5
git_ws add -N app/
```

- `env -u` убирает битые `GIT_CONFIG_*` только на время вызова.
- `git -c safe.directory=/workspace` — one-shot исключение для чужого uid.
- Не задавайте `GIT_CONFIG_KEY_0` вручную и не добавляйте `safe.directory` в
  глобальный конфиг: набор переменных приходит из харнесса и может меняться.
- Не правьте `.git/config` и не пытайтесь «починить» репозиторий — он общий.
- Проверяйте `exit code`: пустой `git status` — нормальный результат, а не
  ошибка.

## Как считать падения git (для LEARN)

Не ищите строку `missing config key GIT_CONFIG_KEY_0` по всему выводу
`tool/result`: она есть в этой памяти и в скилах, и счёт завышается в 1,5–2
раза. Сопоставляйте `toolCallId` результата с `tool/call`, в команде которого
есть `git`, и только там проверяйте `fatal`/`error`. В цикле 10 честный счёт
— 18 падений из 85 git-вызовов; поиск по тексту давал 28.

## Если обёртка не сработала

1. `env | grep -i '^GIT'` — посмотрите, какие переменные пришли.
2. `git_ws rev-parse --show-toplevel` — убедитесь, что виден `/workspace`.
3. Только после этого диагностируйте дальше; не тратьте больше 2–3 шагов на
   инфраструктуру, не связанную с задачей.

Ревьюер в цикле 5 обошёл проблему иначе — `GIT_CONFIG_KEY_0=safe.directory
git ...` (задал недостающий ключ вместо снятия переменных). В этой сессии
сработало, но полагаться на это нельзя: набор `GIT_CONFIG_*` приходит из
харнесса и может измениться. Ревьюер цикла 12 повторил этот обход через
`export GIT_CONFIG_KEY_0=safe.directory GIT_CONFIG_VALUE_0=/workspace` и
потратил на него 2 упавших вызова; обёртка `git_ws` надёжнее.

Помните и про следствие `git add -N`: изменения попадают в индекс, поэтому
обычный `git diff` пуст. В рабочей копии, подготовленной к ревью, смотрите
`git diff HEAD <base>` или `git diff --cached <base>`.

## Цикл 14: разработчик чист, ревьюер снова начал без обёртки

В цикле 14 git вызывался **15 раз** (EXECUTE 4, REVIEW 11), упало **2** —
оба в первых двух вызовах ревьюера (`git status --porcelain`, `git diff
--stat`), затем он перешёл на `unset GIT_CONFIG_*` + `git -c
safe.directory=/workspace` и больше не падал. Разработчик применил `git_ws`
с первого вызова (4/0) — второй чистый EXECUTE после цикла 12 (9/0); это
лучший относительный результат (13 % против 23 % в цикле 13 и 21 % в
цикле 10).

Вывод не меняется, но уточняется адресат: **разработчик уже следует
правилу, ревьюер — нет.** В первой тройке вызовов ревью всегда стоят
`git status`/`git diff`/`git log`; именно там и происходят падения. Если
пишете промпт ревью или начинаете сессию reviewer — первым делом `git_ws`,
не `git`. Цена ошибки небольшая (2 шага из 116), но она повторяется 14
циклов подряд.
