# Оценка размера и прогноз цикла

Паттерн повторялся в циклах 4 и 7: прогноз расхода расходился с фактом в
1,4–5,3 раза. Причина одна — **считали строки и ярлык, а не поверхность
изменения**. T-004 (новая внешняя интеграция) дала 100 шагов против прогноза
50–70; T-007 (allowlist, ярлык S) — 106 шагов против ≤ 20 и 51,7 тыс. output
против ≤ 15 тыс. При этом вилка M «EXECUTE 55–70 + REVIEW 25–40» попала бы в
T-007 точно (70 + 36 = 106). Семь замеров — в
`app/memory/facts/estimate-calibration-m.md` и
`app/memory/facts/estimate-size-s-collapsed-into-m.md`.

## Когда применять

- ANALYZE/PLAN: перед тем как поставить задаче `размер`.
- Intake: когда заявка ещё словами и надо понять, это S, M или L.
- EXECUTE, если ANALYZE не было: первые 2–3 шага — проверка объёма и права
  остановиться/раздробить.
- LEARN: сверить факт с прогнозом и обновить калибровку.

## Процедура

1. **Выпишите поверхность изменения, а не оценку на глаз:**
   - продакшн-файлы, которые придётся создать/изменить;
   - тестовые файлы (это главный предиктор шагов, а не строки);
   - новые внешние контракты: библиотека/API, формат ответа, fallback,
     повторы, валидация чужого ответа, таксономия ошибок;
   - точки проводки: `config` → `bootstrap` → `router`/`cli` → слой.
2. **Определите класс:**
   - **L или дробить** — есть новый чужой контракт, новый пакет/слой,
     > 5 критериев, > 400 строк продакшн-кода/контрактов.
   - **M** — несколько слоёв/точек проводки, 2–5 тестовых файлов, новый
     нейтральный модуль, композиция готовых контрактов.
   - **S** — только ≤ 2 продакшн-файла, ≤ 1 тестовый файл, ≤ 3 критериев,
     без нового модуля и без проводки через сборку/CLI.
3. **Пишите прогноз двумя слагаемыми** (иначе непонятно, что промахнулось):
   - M: `EXECUTE 55–70 + REVIEW 25–40` → 80–110 шагов, 55–110 тыс. output;
   - M с новой внешней интеграцией: `80–120` шагов, `70–100` тыс. output;
   - S (настоящая, по п. 2): `25–40 + 15–25` шагов — это гипотеза, а не
     калибровка; при сомнении выбирайте M;
   - ревью: 30–40 шагов для 4–5 тестовых файлов, 25–40 для 8–9 файлов,
     плюс 5–10 шагов, если handoff сломан.
4. **Проверьте красные флаги:**
   - «S» с 3+ тестовыми файлами — это M (T-007: 5 файлов, 27 кейсов, 106
     шагов);
   - «маленькая задача» с правками в `config` + `handler` + `bootstrap` +
     `cli` — это M, даже если продакшн-кода < 200 строк;
   - output на шаг < 600 — признак многомелких правок, а не дешёвой задачи;
   - diffstat < 500 строк, но 4+ тестовых файлов — ревью всё равно 30–40
     шагов.
5. **Запишите прогноз в задачу/план** и после цикла сравните: шаги, output,
   REVIEW отдельно. Расхождение > 1,3× — повод обновить калибровку фактом,
   а не списать на шум.

## Что не делать

- Не прогнозировать по строкам: T-007 — 145 строк продакшн-кода при 106
  шагах; T-005 — 390 строк сервиса при 94 шагах.
- Не использовать старый потолок «M ≤ 40 шагов / 30 тыс. output»: он не
  достигнут ни разу.
- Не писать «S ≤ 20 шагов» без замера такого класса.
- Не складывать cache read с новым input при оценке стоимости.
- Не считать LEARN частью задачи: он добавляет 50–100 шагов и 50–80 тыс.
  output отдельно (`learn-cost-unaccounted.md`).

## Быстрый шаблон прогноза

```text
Поверхность: <файлы продакшна> / <тестовые файлы> / <новые контракты>
Класс: S | M | L (почему)
EXECUTE: <низ>–<верх> шагов
REVIEW: <низ>–<верх> шагов
Output: <низ>–<верх> тыс.
Риск: <что может добавить 10+ шагов>
```
