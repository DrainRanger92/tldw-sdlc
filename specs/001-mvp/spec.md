# Спецификация 001-mvp — TLDW, MVP

Что именно строим в MVP. Vision и границы продукта — `specs/product.md`;
декомпозиция и порядок работ — `tasks.md` этой спеки.

## Что строим

Telegram-бота **TLDW**, который принимает ссылку на YouTube и возвращает готовую
`.md`-заметку для Obsidian. Пользователь не пересматривает видео и не конспектирует
вручную: бот достаёт транскрипт, сжимает его в структурированную заметку через LLM
и присылает файл в чат.

MVP — один сквозной путь «ссылка → транскрипт → заметка → `.md`-файл» для одного
пользователя или небольшого allowlist. Обработка асинхронная: бот сразу подтверждает
приём, показывает статус и присылает результат, не блокируя другие сообщения.

## Функциональные требования

- **FR-1. Приём ссылки.** Бот принимает текстовое сообщение со ссылкой на YouTube.
  Если ссылки нет — подсказывает формат; если ссылок несколько — обрабатывает первую.
- **FR-2. Валидация ссылки.** Поддерживаются `youtube.com/watch?v=…`, `youtu.be/…`
  и `youtube.com/shorts/…`. Не-YouTube ссылка отвергается отдельной понятной ошибкой.
- **FR-3. Метаданные видео.** Извлекаются название, канал и длительность в секундах,
  когда они доступны.
- **FR-4. Транскрипт.** Транскрипт берётся из субтитров/автосубтитров через
  `youtube-transcript-api`; при сбое — fallback через `yt-dlp`. Отсутствие субтитров —
  отдельная ошибка, отличимая от «не YouTube» и сетевого сбоя.
- **FR-5. Ограничение длительности.** Видео длиннее порога из конфига (дефолт ~2 часа)
  не обрабатывается: пользователь получает понятный отказ, частичная заметка не
  создаётся.
- **FR-6. Генерация конспекта.** Транскрипт с таймкодами отправляется в LLM с жёстким
  промптом на структуру заметки; ответ валидируется до сборки модели заметки.
- **FR-7. Формат заметки.** `.md` совместим с Obsidian: YAML frontmatter (`title`,
  `source`, `channel`, `duration`, `date`, `tags`, `status: processed`) и секции
  `## TL;DR` (3–5 предложений), `## Ключевые идеи` (5–10 пунктов), `## Таймкоды`
  (по смысловым блокам), `## Цитаты` (2–3 с таймкодами), `## Что проверить`.
- **FR-8. Доставка в Telegram.** Сценарий «принял → обрабатываю → готово»: сначала
  подтверждение, затем статус, затем `.md`-документ с безопасным именем файла и
  короткое «готово».
- **FR-9. Понятные ошибки.** Отдельные сообщения на русском для «не YouTube», «нет
  субтитров», «слишком длинное видео», «AI не ответил»; неизвестный сбой — общее
  сообщение пользователю и `ERROR` со стектрейсом в лог.
- **FR-10. Allowlist.** Доступ ограничен списком Telegram user ID из конфига; пустой
  список означает «доступ всем» с предупреждением в лог. Проверка выполняется до
  разбора ссылки и вызовов YouTube/LLM.
- **FR-11. Сохранение результата.** Готовый `.md` сохраняется в каталог данных
  приложения (`app/data/` по умолчанию) до отправки и не попадает в git.

## Нефункциональные

- **Стек.** Python 3.11+, aiogram 3, httpx, youtube-transcript-api, yt-dlp, pytest,
  ruff; точка входа `app/main.py`, логика — пакет `app/tldw/`.
- **Секреты.** `TELEGRAM_BOT_TOKEN`, ключ и модель LLM, allowlist и лимиты — только
  из env/`app/.env`; в код, тесты, фикстуры и логи секреты не попадают.
- **Офлайновые проверки.** `pytest -q` и `ruff check .` проходят без сети и реальных
  токенов; внешние системы подменяются фейковыми адаптерами и `httpx.MockTransport`.
- **Отзывчивость.** Тяжёлые вызовы YouTube/LLM не блокируют event loop Telegram-бота.
- **Надёжность.** Ошибка на любом шаге не оставляет частичную заметку и не роняет
  обработку следующих сообщений; повтор на 429/5xx у LLM ограничен.
- **Приватность.** В логи не пишутся токены, ключи API и полный транскрипт; данные
  приложения лежат в `app/data/` и исключены из git.

## Что НЕ входит в MVP

- Веб-интерфейс, база данных, очередь задач и деплой/хостинг.
- Сохранение копии транскрипта в Obsidian-vault и обновление индекса (v2).
- Поддержка не-YouTube источников и плейлистов.
- Несколько LLM-провайдеров, выбор модели пользователем, биллинг и монетизация.
- Ручное редактирование заметки внутри бота и синхронизация с vault по API.
